# 설계

## 배경

Auto-watch는 Event View 수집과 경기 상태 반영, 예외 저장, 처리 시각 갱신을 담당한다. `auto-watch-status`에는 공통·기존 요청 기록과 예외 파일을 읽고 KST 날짜 및 정각 구간으로 나누는 로직이 있다. 운영 환경은 Oracle VM의 systemd 서비스와 타이머를 사용한다. 변경 목적과 알림 범위는 [제안서](proposal.md)에 있다.

## 목표와 범위

- 운영 알림과 보고서 발행에서 같은 디스코드 웹훅 전송 로직을 사용한다.
- 로컬 기록으로 집계와 조사를 재현할 수 있게 하고, 운영 보고서는 Auto-watch를 중단하지 않고 별도 실행할 수 있게 한다.
- 보고서 첫 발행 범위는 KST 일간 운영 보고서다. 알림 범위는 [실시간 운영 알림 명세](specs/discord-operations-alerts/spec.md)를 따른다.

## 설계 결정

### 수집 결과에서 알림 생성

- Auto-watch에서 이미 분류한 HTTP·저장 오류, Event View의 응답 이슈와 상태 전이, 경기별 예외 종료를 입력으로 사용한다. 저장에 성공한 예외를 기준으로 예외 종료를 알린다. 일시적 장애는 수집 주기당 한 번 세어 같은 주기에 실패 요청이 몰려도 연속 실패 횟수를 한 번만 올린다.
- 별도 주기 점검에서 `heartbeat.json`과 현재 정각 구간의 요청 기록을 읽는다. Heartbeat 허용 지연은 `auto-watch-status`와 같은 `max(수집 간격 × 2, 수집 간격 + 60초)`를 사용한다. 수집기 내부에서도 알린 중단을 다시 감지하면 같은 프로세스의 중단으로 묶는다.
- 첫 구현의 기본값은 일시적 실패와 동일 경기 누락에 각각 연속 3수집 주기, 한 응답의 여러 경기 누락에 2경기, `time_status=2`에 예정 시각 이후 연속 30분 관측이다. 요청량은 기존 종목 분류와 `80%`·`90%` 기준을 사용한다. 이 값들은 기본 동작을 검증할 수 있게 문서에 명시한다.
- 축구는 `timer.md`를 숫자로 정규화해 실제 관측된 구간을 표시한다. 야구는 원문의 `extra.numberofperiods`와 값이 있는 숫자 이닝별 점수를 비교한다. 경기별 연장전 발송 여부와 현재 장애·요청 한도 발송 여부를 별도 로컬 상태에 기록해, 재시작 후에도 이미 보낸 알림을 식별한다. 수집 상태 저장과 알림 상태 저장의 실패 경로를 독립적으로 처리한다.

### 오전 9시 보고서 발행

- `deploy/systemd`에 독립적인 일회성 발행 서비스와 전용 타이머를 둔다. 매일 `00:00:00 UTC`에 예약해 오전 9시(KST)에 실행하고 무작위 지연은 적용하지 않는다. 운영 서버의 로컬 시간대에 관계없이 같은 시각에 예약된다. VM 중단으로 놓친 날짜는 운영자가 대상 KST 날짜를 지정해 수동 발행한다.
- 발행 명령의 기본 대상은 실행 시각을 KST로 변환한 뒤 계산한 전날이다. 요청의 `requested_at`과 예외의 `stopped_at`을 대상 KST 날짜의 UTC 경계로 필터링한다. `auto-watch-status`의 요청·예외 로딩과 종목 분류를 재사용하고, 대상 날짜 안의 정각 구간별 사용률을 계산해 종목별 최대치를 구한다. 혼합·분류 불가 요청은 기존 방식대로 두 종목에 포함한다.
- 동일한 집계 결과에서 디스코드 요약과 Markdown 상세를 만든다. 부분 읽기 실패는 요약과 상세에 표시한다. 로컬 보고서를 먼저 저장하고, 보고서 날짜를 지정한 재발행에는 저장된 파일과 그 요약을 사용한다. 발행에 성공한 날짜는 로컬에 기록해 확인된 성공을 자동 중복 발행하지 않게 한다.

### 디스코드 전송과 운영 설정

- 프로젝트의 HTTP 클라이언트를 사용해 디스코드 웹훅으로 전송한다. 보고서는 요약 카드와 첨부 파일을 하나의 메시지에 담는다. 발송에는 제한 시간을 두고, 전송 오류에는 안전하게 정리한 오류 종류와 상태 코드만 남긴다. 웹훅 URL은 저장소 밖의 systemd 환경 파일에서 주입한다.
- 디스코드에서 수신 결과를 확인한 경우에만 발송을 성공으로 기록한다. 응답을 받기 전에 연결이 끊어지면 실제 발송 여부가 불명확할 수 있으므로 운영자가 채널을 확인하고 저장된 보고서를 재발행할 수 있게 한다.

## 위험과 대응

- 현재 로컬 축구 원문에서는 `timer.md`의 `2·3·4`가 관측되지 않았다. 제공된 매핑을 입력한 오프라인 테스트로 연장 후반이 먼저 관측되는 경우와 승부차기 중복 방지를 검증한다.
- 기존 Discovery 타이머도 오전 9시(KST)부터 실행될 수 있다. 일간 보고서는 전날 KST의 로컬 기록만 집계하므로 당일 Discovery 완료에 의존하지 않는다.
- 보고서 생성이나 전송이 늦거나 실패할 수 있다. 예약 시각은 실행 시작 기준으로 문서화하고, 저장된 보고서와 전송 결과를 확인할 수 있게 한다.

## 배포와 되돌리기

저장된 자료와 대체 웹훅 전송을 사용해 로컬에서 검증하고, Oracle VM 배포 전 systemd 단위와 예약 시각을 검사한다. 운영에서 보고서 발행을 중단할 때는 발행 타이머를 비활성화하고, 실시간 알림을 중단할 때는 알림 설정을 비활성화한다. 발행 실패에 따른 점검과 재발행은 기존 Auto-watch 재시작 정책과 독립적으로 수행한다.

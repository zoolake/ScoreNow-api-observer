# 디스코드 실시간 운영 알림 명세

## Purpose

운영자가 수집 중단과 경기 데이터 누락에 대응할 수 있도록 디스코드에 알린다. 요청 한도에 가까워지는 상황과 확인이 필요한 경기 상태 및 연장전도 알려 준다.

## ADDED Requirements

### Requirement: 수집 장애와 복구 알림

시스템은 HTTP `401·402·403·429`, 운영 설정 오류 또는 로컬 저장 실패로 Auto-watch가 중단되면 즉시 디스코드에 알려야 한다(SHALL). 반복되는 연결 오류와 `5xx`는 지속 기준에 도달했을 때 알리고, 알린 장애가 해소되면 복구를 한 번 알려야 한다. Auto-watch가 멈춰 마지막 처리 기록이 오래됐을 때는 별도 점검에서 알려야 한다.

#### Scenario: 수집을 중단하는 HTTP 오류

- **WHEN** Auto-watch가 Event View 응답에서 HTTP `429`를 받아 수집을 중단한다.
- **THEN** 시스템은 발생 시각, 엔드포인트, HTTP 상태 코드와 수집 중단 사실을 발송한다.

#### Scenario: 연결 장애가 반복된 뒤 복구

- **WHEN** 일시적 실패가 설정된 연속 주기 기준에 도달한 뒤 같은 수집 경로에서 정상 수집이 재개된다.
- **THEN** 시스템은 같은 장애에 대해 경고와 복구를 각각 한 번 발송한다.

#### Scenario: 실행 중인 수집기의 처리 기록이 오래됨

- **WHEN** 별도 점검에서 실행 중으로 기록된 Auto-watch의 마지막 처리 시각이 허용 지연을 초과했다.
- **THEN** 시스템은 마지막 처리 시각을 포함한 알림을 발송한다.

### Requirement: 경기 데이터 누락과 예외 종료 알림

시스템은 정상 HTTP 응답에서 요청한 경기가 반복해서 빠지거나 한 번에 여러 경기가 빠졌을 때 알려야 한다(SHALL). 상태별 관찰 상한에 도달해 경기를 수집 대상에서 예외로 종료했을 때는 마지막 상태와 종료 시각을 알려야 한다.

#### Scenario: 정상 응답에서 수집 대상 경기가 계속 누락됨

- **WHEN** 정상 HTTP 응답에서 같은 경기의 연속 누락 횟수가 기준에 도달한다.
- **THEN** 시스템은 영향받은 경기 ID와 확인 가능한 마지막 정상 수집 시각을 발송한다.

#### Scenario: 경기 시작 대기 상태로 수집 종료

- **WHEN** 예정 시각 이후 관찰 상한에 도달해 `time_status=0`인 경기의 예외 기록을 저장하고 수집을 종료한다.
- **THEN** 시스템은 경기 ID, 마지막 상태와 수집 종료 시각을 발송한다.

### Requirement: 종목별 API 요청 한도 알림

시스템은 저장된 요청 시도 기록을 기준으로 종목별 요청량이 정각 구간의 경고 또는 위험 기준에 도달할 때 각 기준별로 한 번 알려야 한다(SHALL). 해당 구간에 유효한 API 잔여량이 있으면 로컬 요청 수와 함께 표시해야 한다.

#### Scenario: 같은 구간에서 경고와 위험 기준에 도달

- **WHEN** 한 종목의 기록된 요청량이 같은 정각 구간의 경고 기준과 위험 기준에 차례로 도달한다.
- **THEN** 시스템은 각 기준별로 한 번 발송하고, 사용량과 해당 구간을 명시한다.

### Requirement: 특이 경기 상태와 전이 알림

시스템은 Event View에서 `0·1·3` 이외의 상태값과 `3 → 1` 전이를 관측하면 알려야 한다(SHALL). `2`는 설정된 지속 기준을 충족할 때 알려야 한다. 같은 상황이 이어지는 동안에는 알림을 한 번으로 제한해야 한다.

#### Scenario: 정상 종료로 표시된 경기가 다시 경기 중으로 바뀜

- **WHEN** 수집 중인 경기의 `time_status`가 `3`에서 `1`로 바뀐다.
- **THEN** 시스템은 경기 ID, 이전 상태와 현재 상태를 발송한다.

#### Scenario: 시간 미정 상태가 잠깐 관측됨

- **WHEN** `time_status=2`가 지속 기준에 도달하기 전에 다른 상태로 바뀐다.
- **THEN** 시스템은 해당 시간 미정 상태의 알림을 생략한다.

### Requirement: 축구와 야구의 연장전 알림

시스템은 축구의 `timer.md=2` 또는 `3`을 처음 관측할 때 실제로 관측한 연장 전반 또는 연장 후반을 경기당 한 번 알려야 한다(SHALL). `timer.md=4`를 처음 관측하면 승부차기를 별도로 알려야 한다. 야구는 진행 중 응답에 정규 이닝 수를 초과하는 이닝의 점수가 처음 나타날 때 경기당 한 번 알려야 한다.

#### Scenario: 축구 연장 후반이 먼저 관측됨

- **WHEN** 축구 경기에서 `timer.md=2`를 관측한 기록 없이 `timer.md=3`을 처음 관측한다.
- **THEN** 시스템은 연장 후반 최초 관측 알림을 한 번 발송한다.

#### Scenario: 연장전 뒤 승부차기 관측

- **WHEN** 연장전을 이미 알린 축구 경기에서 `timer.md=4`를 처음 관측한다.
- **THEN** 시스템은 승부차기 진입 알림을 한 번 발송한다.

#### Scenario: 야구의 정규 이닝을 초과하는 점수 관측

- **WHEN** `time_status=1`이고 정규 이닝 수가 9인 경기에서 10회 점수가 처음 관측된다.
- **THEN** 시스템은 연장 이닝의 최초 관측을 발송하고, 같은 경기의 이후 연장 이닝으로 반복 발송하지 않는다.

### Requirement: 수집과 알림 발송의 독립성

시스템은 기존 BETS API 호출과 수집의 중단·재시작 정책을 지켜야 한다(SHALL). 디스코드 전송 실패는 수집 상태를 바꾸지 않아야 하며, 알림 메시지와 전송 로그에는 토큰이나 웹훅 URL을 포함하지 않아야 한다.

#### Scenario: 정상 수집 중 디스코드 전송 실패

- **WHEN** 수집 중 보내려던 디스코드 알림의 전송이 실패한다.
- **THEN** 시스템은 비밀 정보를 제외한 전송 실패를 기록하고, 기존 수집 정책에 따라 다음 주기를 처리한다.

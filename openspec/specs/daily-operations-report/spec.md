# daily-operations-report Specification

## Purpose

운영자가 하루 동안의 BETS API 요청량과 수집 오류 및 경기별 예외 종료를 디스코드에서 확인하고, 필요한 경우 첨부 보고서에서 상세 내역을 찾아볼 수 있게 한다.

## Requirements

### Requirement: 매일 오전 9시 디스코드 발행

시스템은 매일 오전 9시(KST)에 전날 KST 일간 운영 보고서 발행을 예약 실행해야 한다(SHALL). 디스코드 메시지 한 건에 요약 카드와 상세 Markdown 파일을 포함해야 한다. 보고서 생성에는 저장된 로컬 기록을 사용해야 한다.

#### Scenario: 정상 예약 발행

- **WHEN** 11월 20일 오전 9시(KST)에 예약 작업이 실행된다.
- **THEN** 시스템은 11월 19일 KST 보고서의 요약 카드와 Markdown 파일을 디스코드에 발행하며, 추가 BETS API를 호출하지 않는다.

### Requirement: KST 날짜별 요청 및 예외 집계

시스템은 대상 날짜의 KST 00:00 이상 다음 날 00:00 미만의 요청 시도와 경기별 예외 종료를 집계해야 한다(SHALL). 보고서는 엔드포인트별 요청 시도 수, 종목별 시간당 최고 사용률, HTTP 오류·연결 실패·완료 기록이 없는 요청, 상태값별 수집 예외 종료 건수를 포함해야 한다. 예외 상세에는 경기 ID·리그·종료 시각을 표시해야 한다.

#### Scenario: KST 자정을 가로지르는 기록

- **WHEN** 대상 날짜의 시작 시각과 다음 날 시작 시각에 각각 요청 기록이 있다.
- **THEN** 시스템은 대상 날짜의 시작 시각에 발생한 요청만 포함한다.

#### Scenario: 저장 기록 일부를 읽지 못함

- **WHEN** 집계 대상인 요청 또는 예외 기록 일부를 읽을 수 없다.
- **THEN** 시스템은 읽은 기록으로 보고서를 작성하고, 요약 카드와 첨부 파일에 부분 집계 사실을 표시한다.

### Requirement: 저장된 보고서의 재발행

시스템은 생성한 보고서를 로컬에 보존하고, 디스코드 전송이 실패하면 같은 대상 날짜의 저장된 보고서를 재발행할 수 있게 해야 한다(SHALL). 보고서 생성 및 발행 실패는 Auto-watch의 수집 상태에 영향을 주지 않아야 한다.

#### Scenario: 전송 실패 후 다시 발행

- **WHEN** 보고서를 저장한 뒤 디스코드 전송이 실패하고 운영자가 대상 날짜를 지정해 재발행한다.
- **THEN** 시스템은 저장된 보고서를 사용해 발행을 다시 시도하고, BETS API를 호출하지 않는다.
